# 3 阶段 TDD（novel-write v3 核心）

> 配合 `SKILL.md` §5 步骤 ④/⑤ 使用。
> 本文件是 novel-write 3 阶段 TDD 的完整规则定义；SKILL.md 仅给关键路径与触发条件。

## 使用路由

- 起草前读“阶段 A”确认细纲与门禁。
- 提交作者前读“阶段 B”做自检。
- 收到反馈后读“阶段 C”和“异常路径”判断回退层级。

---

## 阶段 A：细纲验证（红灯 = 不可写）

**目的**：确保 AI 起草/协写前拿到的输入完整；缺关键字段时停下来询问作者，不得自动补齐。

### 必填 8 字段

每章细纲必须含（顺序不限）：

| 序号 | 字段 | 含义 |
|---|---|---|
| 1 | 核心事件 | 该章要发生的 1 个核心事件 |
| 2 | 冲突类型+双方 | 谁 vs 谁、为何冲突 |
| 3 | 人物动态 | 主要人物的状态变化（情绪/认识/位置）|
| 4 | 爽点类型+强度 | 升级/打脸/揭秘/情感共鸣，强度 1-5 |
| 5 | 节奏标签 | 铺垫 / 冲突 / 高潮 / 收尾 / 日常（5 选 1）|
| 6 | 伏笔操作 | 埋 / 收 / 无关 三选一 + 对应编号 |
| 7 | 关联词条 | 本章涉及的人物/地点/物品词条ID（可附词条名） |
| 8 | 结尾钩子 | 章末抛向下一章的悬念 |

### 必填章节元数据

每章还必须含：

| 字段 | 含义 |
|---|---|
| POV | 本章主视角人物 |
| 场景地点 | 本章主要地点 |
| 故事时间 | 相对时间或明确日期 |
| 出场人物 | 主场/配角/提及人物 |
| 知识库更新标记 | 本章预计更新哪些词条字段 |
| 追踪更新 | 本章预计影响哪些追踪文件 |
| 情节线ID | 本章推进的主线/支线/人物弧光/伏笔线 |
| 场景任务ID | 本章对应 `追踪/写作任务.md` 的任务 |

### 缺任一项的处理

- **缺 1-2 项** → 列出缺项 + 给 2-3 个补法候选 + 询问作者确认
- **缺 ≥3 项** → 回退到 novel-structure 修订细纲
- **缺情节线ID/场景任务ID** → 不进入起草，先补 `追踪/情节线.md` 与 `追踪/写作任务.md`

### workflow_gates.chapters.<场景任务ID>

`workflow_gates.chapter_gate_template` 只定义记录形状；真实门禁必须写入 `workflow_gates.chapters.<场景任务ID>`，避免多个章节共用一个状态。

| 门禁 | 通过条件 | 谁确认 |
|---|---|---|
| outline_ready | 细纲 8 字段、章节元数据、情节线ID、场景任务ID 齐全 | 作者 |
| draft_ready | AI 起草/协写产出正文草稿、摘要、标题候选 | AI 可建议 |
| self_check_passed | 阶段 B 五维自检无红灯 | AI 可建议 |
| human_finalized | 作者确认正文定稿 | 作者 |
| knowledge_reviewed | 知识库提案和追踪更新已人审处理 | 作者 |

AI 只能建议状态变更；需要作者确认的门禁不得自动推进。

### 违反示例 / 修复示例

**违反**：细纲只写"林夜逃跑"（1 项），缺冲突类型/爽点/钩子等。

**修复**：
```
核心事件：林夜在望海镇被玄清弟子追捕，从东市逃到码头
冲突类型+双方：林夜 vs 玄清弟子（执法 vs 逃跑）
人物动态：林夜：紧张 → 决断（化名潜逃）
爽点类型+强度：逃脱追捕 / 4
节奏标签：高潮
伏笔操作：无关
关联词条：CHAR-001 林夜 / LOC-001 望海镇 / FAC-001 玄清
结尾钩子：林夜登船离港时听到船舱内传来说话声"……玄冥剑……"
```

## 阶段 B：5 维自检（红线 → 硬性 → 软性 → 设定 → 伏笔）

**目的**：在提交人审前验证章节草稿，过滤硬伤并列出需要作者裁决的疑点。

### 5 维检查顺序（不可调整）

| 顺序 | 检查类型 | 失败时动作 |
|---|---|---|
| ① 红线 | 12 条铁律（写作约束）| 修订 → 重跑；同条 3 次命中 → 紧急关卡 |
| ② 硬性 | AI 味硬性 Grep（见 de-ai-patterns.md）| 修订 → 重跑 |
| ③ 软性 | AI 味软性（句式/段落/对话自然度）| 列出疑点 → 人审定夺 |
| ④ 设定 | Grep 知识库 → 设定漂移检测 | 修订 → 重跑 |
| ⑤ 伏笔 | 本章伏笔操作 vs `追踪/伏笔.md` | 修订 → 重跑 |

### 5 维 vs superpowers TDD 对位

| novel-write 5 维 | superpowers TDD |
|---|---|
| 红线 | 单元测试（硬拦截）|
| 硬性 | lint 检查（硬约束）|
| 软性 | 集成测试（软约束）|
| 设定 | 集成测试（一致性）|
| 伏笔 | 集成测试（流程完整性）|

### 阶段 B 一次过 vs 重写判断矩阵

| 失败模式 | 一次过？ | 必须重写？ |
|---|---|---|
| 单条红线 1 次命中 | ✓ 局部修改 | |
| 单条红线 ≥3 次命中 | | ✓ 整章重写 |
| 硬性 Grep 命中 >3 处/章 | | ✓ 整章重写 |
| 硬性 Grep 命中 1-3 处/章 | ✓ 局部修改 | |
| 软性疑点（朗读）| ✓ 列出疑点，人审 | |
| 设定漂移（人名/境界/物品冲突）| | ✓ 修订相关段落 |
| 伏笔操作错 | ✓ 修订相关段落 | |

### 异常路径：3 次不过

1. **首次失败**：局部修订 → 重跑阶段 B（仅该条规则）
2. **同条再失败**：换修订策略（局部→更大段）→ 重跑
3. **第 3 次仍失败**：暂停本章写作 → 回 novel-meta 启用"紧急修订模式"（仅修改红线相关字段）

## 阶段 C：人审 4 项红绿灯（最终关卡）

**目的**：在系统自检通过后，以人审直觉把最后一道关。

### 4 项红绿灯

每项打勾 ✓ / ✗：

| 项 | 问什么 | 评价标准 |
|---|---|---|
| **读感** | 节奏/钩子/爽点？| 一口气读完；钩子能撑到下章；爽点密度符合剧情期待 |
| **人物** | 性格/对话/弧光？| 人物行为符合其性格档案；对话不像"两个 AI 在说话" |
| **AI 味** | 自然度/句式变化？| 通顺如人写；句式不重复；无模板句 |
| **钩子** | 章末悬念/章节标题？| 章末能勾住读者；标题有特征 |

### 评分流程

```
主代理：展示 正文草稿 + 本章速览 + 系统自检报告 + 系统疑点 + 2-3 标题方案
↓
人：4 项打勾
↓
全绿 → 人审定稿；任一红 → 携 L1-L4 标签回退
```

### 阶段 C 反模式

- **不要**对所有章都用同一严格度（这是人会累的因素）
- **不要**带情绪评分（今天不爽就给低分）
- **不要**忽略"系统疑点"——系统标的疑点往往抓的是隐性违规

---

## 异常路径汇总

| 失败点 | 默认处理 |
|---|---|
| 阶段 A 缺细纲 | 拒绝写，缺 1-2 项询问作者，缺 ≥3 项回 novel-structure |
| 阶段 B 红线命中 | 修订 → 重跑；3 次不过 → 紧急关卡 |
| 阶段 C 任一红灯 | 回退到 L1-L4 |
| 阶段 C 3 轮不过 | 暂停，询问切换写作策略 |
| 子代理超时 | 重派；2 次失败 → 简化压缩包 |

---

## 与 superpowers TDD 对位

| novel-write | superpowers |
|---|---|
| 阶段 A（细纲） | TDD "test first"——细纲相当于测试 |
| 阶段 B（5 维自检） | TDD "watch it fail"——5 维度量失败 |
| 阶段 B 修订循环 | TDD "make it pass"——反复到绿 |
| 阶段 C（人审）| TDD "refactor"——人审定稿，把最后一道观感 |
| L4 评估前置 | superpowers "receiving-code-review" |

**核心精神**：写作是工程行为——先有可验证的细纲（test），再起草（impl），跑自检（test），人审定稿是 code review。

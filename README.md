# Novel Writer Skills — 网络小说创作辅助工作流

> 定位：网文创作辅助。人做创作决策，AI 只做辅助。

## 为什么不是"一键生成"或自动生产线

大模型的上下文是有限的。即使是最先进的模型，有效上下文窗口也不过几兆 token——而一部网络小说动辄两三百万字。把一本长篇小说塞进上下文让它"读完再写"，技术上做不到。更根本的问题在于，大模型本质是根据输入预测输出——上下文越长，注意力越分散，生成质量越不可控。长篇创作中的"降智"和"前后矛盾"不是 bug，是架构层面的限制。

所以这个项目的目标不是**替代创作者**，而是**放大创作者**：

- **不是**"AI 写一整本小说，人在旁边看"
- **是**"人做创作决策，AI 只做辅助"——提问题、给候选、起草片段、查设定、对伏笔、检AI味、整理审核包

人负责：创意方向、人物灵魂、剧情决策、读感判断、最终定稿。
AI 负责：追问盲点、提供备选方案、协助起草、检查硬伤、整理知识库草稿、追踪伏笔、生成审核包。

**创作辅助的核心**：人的每一次审核都是一次"上下文重置"——AI 不需要记住 200 章的全部内容，它只需要知道"这一章的上下文压缩包 + 人刚才说的反馈"。人的决策是锚点，AI 的起草、检查、整理都围绕这个锚点展开。

## 谁适合用 / 谁不适合

**适合**：
- 有长篇写作经验，但被 AI 辅助流程反复打脸的中文网文老作者
- 正在连载，需要保持人物/设定/伏笔跨卷一致性
- 愿意投入审核时间来换取长篇可控性

**不适合**：
- 想躺平让 AI 写完一整本的人——这套工具要求作者深度参与
- 写严肃文学、成人向、文学性实验作品——铁律默认面向中文网文平台过审标准
- 短篇/单本作者——这套流程的边际收益在百章之后才充分显现

铁律可通过 `novel-config.json` 按需开关。用户画像和平台适配见 config 中 `user_persona` 字段。

## 使用方式

安装后，在 Claude Code（或其他支持的 Agent）中直接用自然语言操作。

### 从零开始

```
你："帮我构思一部修仙小说"
→ AI 启动 novel-ideate，询问题材/主角/金手指/冲突/篇幅
→ 你回答5个问题 → AI 生成书名、简介、卖点
→ 你确认 → 进入设定期
```

### 带着创意来

```
你："我想写一个炼丹师被害重生、带着因果之眼回去复仇的故事"
→ AI 启动种子模式，追问没覆盖的维度
→ 在你创意基础上补全 → 你确认
```

### 设计世界和人物

```
你："开始设定"
→ AI 启动 novel-design，逐模块构建世界观→人物→力量体系→物品→关系
→ 每模块你确认或修改
```

### 规划大纲

```
你："做大纲"
→ AI 启动 novel-structure，主线→地图→章节细纲
→ 每层你确认
```

### 写章节

```
你："开始写第一章"
→ AI 准备上下文压缩包 → AI起草/协写正文草稿
→ AI 系统自检（铁律+AI味）→ 提交给你审
→ 你说"通过"或"林夜的对话太啰嗦了[改章节]"
→ AI 修改 → 你确认 → 写入知识库暂存区
→ 你审核暂存词条 → AI 入库并更新索引
```

### 继续创作

```
你："继续下一章"
→ AI 读取进度.json + 写作任务矩阵 + 门禁状态
→ 汇报下一章候选与未完成门禁 → 你确认后起草草稿
```

### 断点续作

```
你："继续写《剑道独尊》"
→ AI 读取项目进度.json → 汇报当前进度 → 从断点继续
```

### 跨模型审核

```
你："发审核包给Gemini审一下"
→ AI 生成审核包 → 你复制给Gemini → 贴回结果 → AI合并
```

### 大局复盘

```
（每50章自动提醒）
→ AI："已完成50章，是否进行周期性复盘？"
→ AI六维度扫描 → 生成复盘报告 → 你决策
```

## 技能构成

| 技能 | 类型 | 阶段 / 用途 | 入口提示 |
|------|------|-------------|---------|
| `novel-ideate` | 核心创作 | 构思期 | "帮我构思一部小说" 或 直接描述你的创意 |
| `novel-design` | 核心创作 | 设定期 | "开始设定" 或 "设计世界观/人物/力量体系" |
| `novel-structure` | 核心创作 | 大纲期 | "做大纲" 或 "规划主线/地图/细纲" |
| `novel-write` | 核心创作 | 创作审核期 | "开始写第X章" 或 "继续写" 或 "发审核包" |
| `inspiration` | 支撑 | 灵感捕获与讨论 | "灵感：..." / "讨论这个灵感" |
| `agent-dispatch` | 支撑 | 隔离上下文起草 / 并行审计流程 | 通常由其他 skill 调用 |
| `novel-meta` | 支撑 | skill/config/template 审计与演进 | "审计 novel-write" / "调整 novel-config" |

## 完整工作流

```
构思 → 设定 → 大纲 → 写作+审核
  ↑       ↑       ↑         ↑
 人审    人审    人审      人审+铁律自检

写作循环（每章）：
  细纲 + 追踪状态 → 准备上下文压缩包 → AI起草/协写章节(可隔离上下文)
  → AI系统自检(铁律+AI味) → 提交人审
  → 人反馈 → AI修改 → 人确认
  → 知识提取(人审入库) + 追踪更新 + 决策日志 + 章节标题 + 摘要
```

## 关键机制

### 三层上下文 + 追踪系统
长篇写作不能靠模型记忆硬撑。本项目把上下文拆成三层，并单独保留追踪层：

- **标准层**：`novel-config.json`、铁律、平台节奏、审核阈值
- **故事层**：核心概念、正式 `知识库/` 词条、决策日志
- **章节层**：当前 L3 细纲、章节元数据、最近摘要、写前查询包
- **追踪系统**：`追踪/当前上下文.md`、`追踪/伏笔.md`、`追踪/时间线.md`、`追踪/角色状态.md`、`追踪/情节线.md`、`追踪/写作任务.md`

写章节前，AI 先从三层上下文和追踪系统组装压缩包；写章节后，AI 只提出知识库变更提案和追踪更新建议。正史入库、章节定稿、方向调整都必须由人审。

### 情节线 / 场景任务矩阵
`追踪/情节线.md` 记录主线、支线、人物弧光、关系线和伏笔线，每条线都有 `情节线ID`。`追踪/写作任务.md` 记录每章/场景的 `场景任务ID`、目标字数、当前状态、门禁和下一步。

细纲不是孤立章节列表；每章要说明它推进了哪条情节线、完成了哪个场景任务。这样“继续写”时，AI 不只看 `current_chapter`，还要检查哪些线断了、哪些任务卡在自检或人审。

### 状态机与人审门禁
`进度.json.workflow_gates` 是状态机，不是自行流转器。AI 只能建议状态变更；凡是 `human_approved`、`human_finalized`、`knowledge_reviewed`、`checks.*_done` 相关动作，都必须等作者明确确认。

阶段门禁放在 `workflow_gates.ideate/design/structure`。章节门禁放在 `workflow_gates.chapters.<场景任务ID>`，并按 `chapter_gate_template` 建记录；不使用单例 `chapter`，否则上一章、当前章和下一章会互相覆盖。

章节门禁顺序：

```text
outline_ready → draft_ready → self_check_passed → human_finalized → knowledge_reviewed
```

任何一步失败都写 `blocked_reason`，提交作者决定：改章节、改细纲、改设定、暂存观察或人工接管。

`current_chapter = 已定稿章节号`。大纲规划到第几章看 `phases.structure.total_chapters_planned` 和 `追踪/写作任务.md`，不要用 `current_chapter` 代表大纲游标。

### 铁律检查（三层关卡）
12条创作红线（主角不死/不换主角/不涉黄涉政/不涉黑毒赌/信息屏蔽…），在设计→大纲→写作三层拦截，违规即修正。

### 对标/拆文证据链
构思期可以参考平台榜单、同类爆款、作者自带样本或历史作品拆文，但排行榜不是结论。AI 必须标注对标样本来源、拆文观察、证据等级，以及哪些判断只是推测；作者再决定是否吸收。

### AI味审核（四层）
- 红线：创作提示词泄漏（6类Grep模式，命中即退回）
- 硬性：高频过渡词、模板化情感、形容词堆砌（Grep阈值检测）
- 软性：句式变化、段落节奏、对话自然度（朗读检查）
- 全局：终审随机抽样5章，对比句式演进和词汇多样性

### Karpathy-style 知识库
结构化 Markdown + Grep 精准查询。知识库不是草稿箱，而是项目正史：正式词条供写作查询，暂存区放待确认提案，决策日志记录会影响后续创作方向的选择。

知识流转：

```text
设定草稿 → 人审确认 → 正式词条 → _index.md 同步
       → 写前查询 → 章节压缩包 → 正文草稿
       → 写后提取 → 暂存区提案 → 人审入库
       → 决策日志（仅重大方向变更）
```

写前查询先读 `_index.md`，再按 `关联词条` 读取具体人物、地点、势力、物品、概念。写后提取只生成变更提案；人不审，AI 不把暂存区内容移入正式知识库。

### 子代理上下文隔离
写章节时只传入压缩上下文包（细纲 + 前情叙事(≤300字) + 词条快照 + 追踪提醒），隔离历史上下文，避免长篇小说上下文膨胀。子代理只是起草与检查工具，不能替作者定稿。

### 周期性大局复盘
每50章/每地图结束，6大维度扫描：人物漂移、伏笔审计、节奏健康、世界一致性、关系线、知识库同步。

## 审查角色

| 谁审 | 审什么 |
|------|--------|
| **AI系统自检** | 铁律红线 + AI味硬性模式 + 设定一致性 + 伏笔连续性 |
| **你（作者）** | 读感、爽点、人物、钩子、AI味——凭直觉，不逐条打勾 |
| **你（每地图）** | 地图目标达成、主角成长、节奏、衔接 |
| **你（每50章）** | 人物漂移、伏笔审计、世界一致性——大局复盘 |
| **你（终审）** | 5维度最终裁决——通过/有条件通过/退回 |

## 校验

在技能仓库中运行各 `scripts/validate_*.py --all` 检查技能与模板，运行 `python3 -m unittest discover -s scripts -p 'test_*.py'` 执行校验器回归测试。

检查小说项目时，使用技能仓库内脚本的实际路径，并将参数指向小说项目或刚修改的文件：

```bash
python3 /path/to/novel-writer-skills/scripts/validate_novel_project.py --project-root /path/to/novel
python3 /path/to/novel-writer-skills/scripts/validate_assets.py --template novel-config --file /path/to/novel/novel-config.json
python3 /path/to/novel-writer-skills/scripts/validate_assets.py --template character --file /path/to/novel/知识库/人物/角色名.md
```

`--file` 支持 `novel-config`、`character`、`location`、`faction`、`item`、`concept`。省略它时只检查仓库模板。项目检查会核对实际配置、正式词条、门禁顺序、阶段完成状态，以及每章细纲与情节线、写作任务矩阵的绑定。

技能仓库自身的审计使用模板即可；只有审查真实小说的运行状态时才需要指定小说项目。
